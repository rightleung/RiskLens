## 优先级 1：/api/v1/assess 的建议查询失败会覆盖主错误并升级为 500

### 问题现象

当单个 ticker 的主评估已经被正确捕获为 `DataFetchError`、`AssessmentServiceError` 或 timeout 时，如果随后用于返回候选 ticker 的 suggestions 查询抛出未被捕获的异常，整个 `/api/v1/assess` 请求会变成全局 500，而不是返回原本的 404/422/504/503。

### 根因分析

- 文件：`src/api.py`
- 关键代码：
  - `fetch_suggestions()` 只捕获 `TimeoutError, DataFetchError, KeyError, AttributeError`：`src/api.py:432-440`
  - 多个异常分支在返回错误对象之前先执行 `sugg = await fetch_suggestions(ticker)`：`src/api.py:464-496`
  - `asyncio.gather(*tasks)` 未设置 `return_exceptions=True`，子任务中的 suggestions 异常会直接打断整个请求：`src/api.py:519-520`

### 触发条件

- `_analyze_single_ticker()` 已失败并进入 `except DataFetchError`、`except AssessmentServiceError`、`except TimeoutError` 或 `except Exception`。
- `_search_tickers()`、`_run_in_fetch_executor()` 或 yfinance search 在 suggestions 阶段抛出 `RuntimeError`、`ValueError`、`TypeError`、`UpstreamCapacityError` 等未被 `fetch_suggestions()` 捕获的异常。

### 为什么会发生

错误处理分支本身又执行了一个可能失败的外部调用。这个外部调用的异常白名单太窄，且异常发生在 `except` 块内部，不会被同一个 `try` 的后续 `except` 分支接住，最终冒泡到 `asyncio.gather()` 和全局异常处理器。

### 修复方案

1. 在 `src/api.py:432-440` 把 `fetch_suggestions()` 改成“失败即返回空列表”的绝对降级函数。
2. 明确捕获 `UpstreamCapacityError`、`TimeoutError`、`DataFetchError` 和通用 `Exception`，通用异常只写日志，不向响应暴露细节。
3. 给这个分支加回归测试：主评估抛 `DataFetchError`，`_search_tickers` 抛 `RuntimeError`，接口应返回 `all_tickers_failed` 的 404/422/503/504，而不是全局 500。

### 验收标准

- 新增测试覆盖 suggestions 失败不会覆盖主错误。
- `/api/v1/assess` 在 suggestions 异常时仍返回稳定的 per-ticker 错误结构。
- 响应体不包含 suggestions 的原始异常字符串。

## 优先级 2：symbol search 的“第二次清代理重试”被异常类型短路

### 问题现象

`/api/v1/symbols/search` 和 `/assess` 的 suggestions 本意是 yfinance search 第一次失败后第二次清理代理环境再试一次，但网络、proxy、curl、timeout 类异常不会进入第二次尝试。

### 根因分析

- 文件：`src/api.py`
- 关键代码：
  - `for attempt in range(2)` 定义了两次尝试：`src/api.py:667`
  - 第二次尝试才设置 `clear_proxy=True`：`src/api.py:669`
  - 但 `except` 只捕获 `KeyError, AttributeError, TypeError, ValueError`：`src/api.py:703-705`

### 触发条件

yfinance `Search` 或 `run_yfinance_call()` 在第一次尝试中抛出 `RuntimeError`、连接异常、curl/proxy 异常或其他非白名单异常。

### 为什么会发生

第一次尝试抛出的网络异常没有被 `_search_tickers()` 捕获，循环直接退出，导致 `attempt == 1` 的清代理分支永远不执行。

### 修复方案

1. 在 `src/api.py:703-705` 扩大捕获范围，至少捕获 `Exception` 并记录 `last_error`。
2. 区分 `strict=True` 和 `strict=False`：
   - `strict=False`：所有 search 异常返回 `[]`。
   - `strict=True`：两次均失败后抛出最后一个异常，由 endpoint 统一转成 503。
3. 保留日志，但不要在 API 响应中暴露底层异常内容。

### 验收标准

- 新增单元测试证明第一次 search 抛 `RuntimeError("proxy failure")` 时会进入第二次 `clear_proxy=True` 尝试。
- suggestions 场景下同样异常返回 `[]`，不会中断主评估响应。

## 优先级 3：PDF 导出没有请求级超时，慢渲染会长期占用 executor 容量

### 问题现象

`/api/v1/reports/pdf` 对 PDF 渲染没有 `asyncio.wait_for` 包裹。大 payload、复杂 ReportLab 布局或渲染卡住时，请求会等待到渲染函数结束，并持续占用 `_FETCH_CAPACITY`。

### 根因分析

- 文件：`src/api.py`
- 关键代码：
  - assess 和 covenant 都用 `asyncio.wait_for(..., timeout=per_ticker_timeout)`：`src/api.py:446-450`、`src/api.py:847-849`
  - PDF 导出直接 `await _run_in_fetch_executor(generate_full_pdf, report, lang, theme)`，没有 timeout：`src/api.py:898-899`
  - `_run_in_fetch_executor()` 的 semaphore 只有在线程任务结束后才释放：`src/api.py:213-218`

### 触发条件

PDF payload 接近上限、statement/detail rows 较多、ReportLab 渲染异常慢，或渲染函数因布局/字体问题卡住。

### 为什么会发生

PDF 渲染复用了受限 executor，但没有和其他阻塞路径一样设置请求等待上限。即使客户端超时断开，底层线程也可能继续运行并占用 capacity。

### 修复方案

1. 在 `src/config.py` 新增 `pdf_export_timeout_seconds: float = 20.0`，并用 Pydantic 约束为正数。
2. 在 `src/api.py:898-899` 外层加 `asyncio.wait_for(..., timeout=settings.pdf_export_timeout_seconds)`。
3. 捕获 `TimeoutError`，返回 504，`error_type="timeout"`。
4. 新增 API 测试：mock `generate_full_pdf` 慢执行，mock `asyncio.wait_for` 抛 timeout，接口应返回 504。

### 验收标准

- PDF 超时返回 504。
- capacity exhaustion 仍返回 503。
- 正常 PDF 导出测试仍通过。

## 优先级 4：single-flight 等待没有超时，失败或卡死的上游会放大为线程池耗尽

### 问题现象

同一个 ticker/source 并发请求时，后续线程会在 `event.wait()` 上无期限等待第一个线程。如果第一个线程卡在 yfinance/AKShare 调用中，API 层 `wait_for` 会让请求返回 timeout，但底层 worker 仍卡住并占用 executor capacity。

### 根因分析

- 文件：`src/data_fetcher.py`
- 关键代码：
  - single-flight 事件表：`src/data_fetcher.py:164-166`
  - 等待 in-flight 无 timeout：`src/data_fetcher.py:976-991`
  - API 注释已说明 `asyncio.wait_for` 不能取消运行中的 OS 线程：`src/api.py:186-190`

### 触发条件

同 ticker/source 的并发请求中，第一个上游 fetch 长时间不返回或卡死，第二个及后续请求进入 `event.wait()`。

### 为什么会发生

single-flight 只解决并发击穿，但没有等待时限、失败传播状态或 stale in-flight 清理。API 请求超时不等于 worker 线程停止，worker 继续占用 `_FETCH_CAPACITY`，高并发下会导致大量 503 `upstream_busy`。

### 修复方案

1. 在 `src/config.py` 增加 `single_flight_wait_timeout_seconds`，默认不超过 `assess_ticker_timeout_seconds`。
2. 在 `src/data_fetcher.py:976-991` 使用 `event.wait(timeout=...)`。
3. wait 超时后抛 `DataFetchError(error_type=NETWORK_ERROR, details={"reason": "single_flight_timeout"})`。
4. 可选增强：`_in_flight` 从 `dict[str, Event]` 改为保存开始时间和异常状态，便于等待方复用失败原因而不是重复发起请求。

### 验收标准

- 新增测试：第一个同 ticker fetch 卡住，第二个等待超过 single-flight timeout 后抛 `DataFetchError`，不会无限挂起。
- 现有 single-flight coalescing 测试仍通过。

## 优先级 5：季度 Z-Score fallback 复制了整份年度 assessment，导致季度结果混入年度指标

### 问题现象

当季度期间无法计算 Z-Score、但最近年度期间能计算时，代码把整份年度 `assessment` 复制到季度 entry。这样季度 entry 的 `risk_score`、`zscore_breakdown`、`strengths`、`weaknesses` 和 `covenant_pre_check` 都可能来自年度，而不是季度。

### 根因分析

- 文件：`src/services/rich_assessment_service.py`
- 关键代码：
  - 最新有效年度 assessment 被保存：`src/services/rich_assessment_service.py:108-109`
  - 季度 N/A 时直接 `entry["assessment"] = dict(latest_fy_assessment)`：`src/services/rich_assessment_service.py:163-169`

### 触发条件

季度数据缺少 `total_assets`、`total_liabilities`、`working_capital`、`operating_income` 或 `sales` 中任一 Z-Score 必需项，导致季度 `overall_rating == "N/A"`；同时最近年度 assessment 有有效评级。

### 为什么会发生

需求是“季度评级 fallback 到 FY”，但实现粒度是整对象替换，不只是替换评级字段。下游 UI/PDF 会把季度行展示成年度 covenant/strengths/zscore breakdown。

### 修复方案

1. 不再替换整份 `assessment`。
2. 仅复制 `overall_rating`、`implied_rating`，必要时复制一个 `rating_fallback_source` 字段。
3. 保留季度自己的 `risk_score`、`zscore_breakdown`、`covenant_pre_check`、`strengths`、`weaknesses`。
4. 如果 `risk_score` 不可算，继续为 `0.0` 或改成 `None`，但必须明确 `zscore_status="fallback_rating_only"`。

### 验收标准

- 新增 RichAssessmentService 测试：季度 Z-Score N/A + 年度有效时，季度只 fallback rating，不复制年度 covenant rows。
- PDF/JSON 中能看见 fallback 来源，不把季度指标伪装成年度指标。

## 优先级 6：total_debt 不做派生，导致可用债务字段被丢弃

### 问题现象

如果数据源没有提供 `total_debt`，但提供了 `short_term_debt`、`long_term_debt`、`current_portion_lt_debt` 或 `bonds_payable`，多个杠杆和现金流比率会显示 N/A。

### 根因分析

- 文件：`src/ratio_analyzer.py`
- 关键代码：
  - yfinance 映射包含多个债务字段：`src/data_fetcher.py:359-366`
  - ratio 计算只读取 `total_debt`：`src/ratio_analyzer.py:780-831`
  - cash flow ratio 也只读取 `total_debt`：`src/ratio_analyzer.py:957-966`

### 触发条件

上游 statement 有短债/长债但没有总债字段；这在不同市场、不同 yfinance 字段版本和 AKShare/yfinance fallback 混合数据中都可能发生。

### 为什么会发生

字段标准化层保留了债务组成项，但 ratio 层没有总债派生逻辑，导致下游 `debt_to_assets`、`debt_to_ebitda`、`fcf_to_debt` 断算。

### 修复方案

1. 在 `RatioAnalyzer` 增加 `_derive_total_debt(bs_data)`。
2. 优先使用显式 `total_debt`；缺失时用短债、长债、一年内到期非流动负债、应付债券求和。
3. `calculate_leverage_ratios()` 和 `calculate_cash_flow_ratios()` 统一使用该 helper。
4. 保持全缺失时返回 `None`。

### 验收标准

- 新增测试：只有 short/long debt 时，`debt_to_assets`、`debt_to_ebitda`、`fcf_to_debt` 可正常计算。
- AKShare 既有派生行为不回归。
